================================================================================
GUIA DE INSTRUCOES PARA MIGRACAO DO BANCO DE DADOS: H2 PARA POSTGRESQL
Projeto: API Almoxarifado (devcom)
================================================================================

Este documento descreve os passos necessarios para realizar a futura migracao do
banco de dados da aplicacao, saindo do H2 (banco em memoria utilizado em desenvolvimento)
para o PostgreSQL (banco relacional robusto para ambientes de homologacao e producao).

--------------------------------------------------------------------------------
1. CRIACAO DO BANCO DE DADOS E USUARIO NO POSTGRESQL
--------------------------------------------------------------------------------
Acesse o terminal do PostgreSQL via psql ou ferramenta de administracao (ex: pgAdmin,
DBeaver) utilizando uma conta de superusuario (ex: postgres):

  -- 1.1 Criar o usuario da aplicacao com senha segura
  CREATE USER almox_user WITH ENCRYPTED PASSWORD 'coloque_aqui_uma_senha_forte';

  -- 1.2 Criar o banco de dados dedicado ao almoxarifado
  CREATE DATABASE almoxarifado_db
      WITH
      OWNER = almox_user
      ENCODING = 'UTF8'
      LC_COLLATE = 'pt_BR.UTF-8'
      LC_CTYPE = 'pt_BR.UTF-8'
      TABLESPACE = pg_default
      CONNECTION LIMIT = -1;

  -- 1.3 Conceder privilegios necessarios
  GRANT ALL PRIVILEGES ON DATABASE almoxarifado_db TO almox_user;

  -- Para PostgreSQL versao 15 ou superior, garanta acesso explicito ao schema public:
  \c almoxarifado_db
  GRANT ALL ON SCHEMA public TO almox_user;
  GRANT USAGE, CREATE ON SCHEMA public TO almox_user;

--------------------------------------------------------------------------------
2. ADICAO DO DRIVER POSTGRESQL AO PROJETO (pom.xml)
--------------------------------------------------------------------------------
No arquivo pom.xml, adicione a dependencia oficial do driver JDBC do PostgreSQL no
bloco <dependencies>.

Exemplo:
  <!-- Driver JDBC do PostgreSQL para conexao em tempo de execucao -->
  <dependency>
      <groupId>org.postgresql</groupId>
      <artifactId>postgresql</artifactId>
      <scope>runtime</scope>
  </dependency>

Nota: Caso queira manter o perfil H2 ativo para testes unitarios locais, mantenha o H2
com scope test ou configure profiles do Maven/Spring Boot.

--------------------------------------------------------------------------------
3. CONFIGURACAO DAS VARIAVEIS DE AMBIENTE
--------------------------------------------------------------------------------
Nunca armazene credenciais sensiveis em texto puro no codigo-fonte ou no Git.
Utilize variaveis de ambiente no sistema operacional, Docker ou servidor CI/CD:

- DB_HOST: Host onde o PostgreSQL esta executando (ex: localhost ou postgres-db)
- DB_PORT: Porta de conexao (padrao: 5432)
- DB_NAME: Nome do banco de dados (ex: almoxarifado_db)
- DB_USERNAME: Usuario de conexao (ex: almox_user)
- DB_PASSWORD: Senha do usuario do banco

Exemplo de exportacao de variaveis:
- Linux / macOS / Bash:
    export DB_HOST=localhost
    export DB_PORT=5432
    export DB_NAME=almoxarifado_db
    export DB_USERNAME=almox_user
    export DB_PASSWORD=coloque_aqui_uma_senha_forte

- Windows (PowerShell):
    $env:DB_HOST="localhost"
    $env:DB_PORT="5432"
    $env:DB_NAME="almoxarifado_db"
    $env:DB_USERNAME="almox_user"
    $env:DB_PASSWORD="coloque_aqui_uma_senha_forte"

- Docker Compose:
    environment:
      - DB_HOST=postgres
      - DB_PORT=5432
      - DB_NAME=almoxarifado_db
      - DB_USERNAME=almox_user
      - DB_PASSWORD=coloque_aqui_uma_senha_forte

--------------------------------------------------------------------------------
4. AJUSTE DA CONFIGURACAO DO SPRING BOOT (application.properties / application-prod.properties)
--------------------------------------------------------------------------------
Recomenda-se criar um perfil especifico para producao (ex: application-prod.properties)
ou parametrizar o application.properties utilizando as variaveis de ambiente:

  # Conexao com o Banco de Dados PostgreSQL
  spring.datasource.url=jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:almoxarifado_db}
  spring.datasource.username=${DB_USERNAME:almox_user}
  spring.datasource.password=${DB_PASSWORD}
  spring.datasource.driver-class-name=org.postgresql.Driver

  # Propriedades do JPA / Hibernate
  spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect
  spring.jpa.open-in-view=false

  # Estrategia de DDL (VALIDATE ou NONE para ambientes com migrations)
  spring.jpa.hibernate.ddl-auto=validate
  spring.jpa.show-sql=false

--------------------------------------------------------------------------------
5. VALIDACAO DOS RELACIONAMENTOS E RESTRICOES NO POSTGRESQL
--------------------------------------------------------------------------------
Apos inicializar a aplicacao ou executar o script inicial, valide no PostgreSQL se o
esquema respeita todas as regras e integridades definidas nas entidades JPA:

  - Tabela 'users':
      * Chave primaria: id (BIGSERIAL / IDENTITY)
      * Chave candidata/Unica: cpf (UNIQUE, NOT NULL, VARCHAR(14))
      * Colunas obrigatorias: name (VARCHAR(150)), password (VARCHAR(255)), role (VARCHAR(20))
  - Tabela 'products':
      * Chave primaria: id
      * Coluna barcode (VARCHAR(64), UNIQUE, aceitando nulos para produtos sem codigo de barras)
      * Coluna description mapeada como tipo TEXT nativo
      * Coluna unit (VARCHAR(20), NOT NULL)
  - Tabela 'product_batches':
      * Chave primaria: id
      * Chave estrangeira: product_id referenciando products(id) (ON DELETE RESTRICT / NO ACTION)
      * Coluna quantity: NUMERIC(19, 4), NOT NULL
      * Coluna batch_code e expiration_date opcionais
  - Tabela 'stock_movements':
      * Chave primaria: id
      * Chaves estrangeiras: user_id referenciando users(id) e batch_id referenciando product_batches(id)
      * Coluna type (VARCHAR(20), NOT NULL)
      * Coluna quantity: NUMERIC(19, 4), NOT NULL
      * Coluna created_at: TIMESTAMP NOT NULL (gerado automaticamente no cadastro)
      * Coluna observation: TEXT

Recomenda-se executar a suite de testes automatizados com Spring Boot Test utilizando
o Testcontainers com imagem oficial do PostgreSQL (ex: postgres:16-alpine) para garantir
que todas as consultas e constraints funcionem exatamente igual ao ambiente real.

--------------------------------------------------------------------------------
6. PLANEJAMENTO DE MIGRACAO DOS DADOS (H2 -> POSTGRESQL)
--------------------------------------------------------------------------------
Caso existam dados no H2 que precisem ser preservados na migracao:

  6.1 Exportacao do H2:
      Execute no console H2:
      SCRIPT TO 'backup_h2.sql' TABLE users, products, product_batches, stock_movements;

  6.2 Tratamento e Limpeza:
      - Remova sintaxes proprietarias do H2.
      - Assegure-se de que os dados de texto longo estejam codificados em UTF-8.
      - Verifique se os formatos de data e hora (LocalDate, LocalDateTime) estao no padrao ISO-8601.

  6.3 Ordem de Importacao (respeitando a integridade referencial):
      1. Tabela 'users' e Tabela 'products' (entidades raiz, sem dependencias)
      2. Tabela 'product_batches' (depende de products)
      3. Tabela 'stock_movements' (depende de users e product_batches)

  6.4 Atualizacao das Sequences no PostgreSQL:
      Ao inserir registros com IDs explicitos no PostgreSQL, as sequences automaticas
      precisam ser sincronizadas com o valor maximo existente para evitar erros de chave duplicada:
      SELECT setval(pg_get_serial_sequence('users', 'id'), COALESCE(MAX(id), 1)) FROM users;
      SELECT setval(pg_get_serial_sequence('products', 'id'), COALESCE(MAX(id), 1)) FROM products;
      SELECT setval(pg_get_serial_sequence('product_batches', 'id'), COALESCE(MAX(id), 1)) FROM product_batches;
      SELECT setval(pg_get_serial_sequence('stock_movements', 'id'), COALESCE(MAX(id), 1)) FROM stock_movements;

--------------------------------------------------------------------------------
7. POR QUE EVITAR 'ddl-auto=update' EM PRODUCAO
--------------------------------------------------------------------------------
O uso de 'spring.jpa.hibernate.ddl-auto=update' em ambientes produtivos apresenta
altos riscos operacionais:

  - Nao remove colunas nem tabelas obsoletas: O Hibernate nunca remove colunas ou
    constraints antigas para evitar perda de dados, gerando acumulo de estruturas mortas.
  - Bloqueios de tabelas (Locking): Modificacoes automaticas de DDL durante a subida
    da aplicacao podem aplicar locks exclusivos em tabelas grandes, causando lentidao
    ou indisponibilidade (downtime).
  - Falta de controle de versao e rastreabilidade: Nao ha historico de quem aplicou a
    mudanca, quando foi aplicada ou qual era o estado anterior.
  - Risco de corrupcao ou alteracoes silenciosas: Tipos de colunas podem ser alterados
    de forma incompativel sem validacao previa.
  - Comportamento imprevisivel em ambientes clusterizados: Se multiplas instancias da
    aplicacao subirem simultaneamente, concorrencia na execucao de DDL pode corromper
    o catalogo do banco de dados.

Estrategia correta:
Em producao, utilize 'spring.jpa.hibernate.ddl-auto=validate' (para garantir que a
estrutura do banco bate com as entidades) ou 'none'.

--------------------------------------------------------------------------------
8. ADOCAO DE FERRAMENTAS DE MIGRACAO DE BANCO (FLYWAY OU LIQUIBASE)
--------------------------------------------------------------------------------
Para gerenciar a evolucao do esquema de forma profissional, segura e auditavel, deve-se
adotar uma ferramenta de Database Migration. O Flyway e altamente recomendado pela sua
simplicidade e integracao nativa com o Spring Boot.

  8.1 Como adicionar o Flyway:
      Adicione no pom.xml:
      <dependency>
          <groupId>org.flywaydb</groupId>
          <artifactId>flyway-core</artifactId>
      </dependency>
      <dependency>
          <groupId>org.flywaydb</groupId>
          <artifactId>flyway-database-postgresql</artifactId>
      </dependency>

  8.2 Estrutura de Scripts Versionados:
      Crie os scripts SQL dentro do diretorio:
      src/main/resources/db/migration/

      Padrao de nomenclatura:
      V1__create_tables_initial_schema.sql
      V2__create_indexes.sql
      V3__add_new_column_example.sql

  8.3 Vantagens:
      - Scripts SQL puros e explicitos testados e revisados por Code Review.
      - Tabela de controle 'flyway_schema_history' que registra checksum, data, autor e status.
      - Execucao automatica, transacional e idempotente durante o boot do Spring Boot.
      - Permite esteiras de CI/CD aplicarem mudancas de forma confiavel antes ou durante o deploy.
